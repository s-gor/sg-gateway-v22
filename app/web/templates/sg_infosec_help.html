Что защищает SG InfoSec

SG InfoSec — локальный модуль защиты административной части сервера. Он не имеет публичного сетевого API и взаимодействует с SG-Gateway через Unix-сокеты.

  • SSH: обнаруживает перебор паролей, медленный brute force и перебор имён пользователей; подтверждённые адреса блокируются через nftables только на TCP/22.
  • Вход в панель: учитывает ошибки авторизации и применяет решения к области admin-login.
  • API панели: учитывает ошибки авторизации, сканирование служебных маршрутов и решения области admin-api.
  • HTTP-запросы: фильтрует высокоуверенные признаки SQL injection, XSS, path traversal, command injection, опасные методы и известные пути сканеров.
  • Корреляция: объединяет события одного IP из SSH, Nginx и SG-Gateway.
Изоляция VPN Правила SG InfoSec не должны затрагивать AWG, подписки и VPN-порты 585–587. SSH-решения ограничены TCP/22, а вход и API блокируются приложением.

Автоматическая защита

Сервис читает только новые записи журналов ssh.service, sshd.service, nginx.service и sg-gateway.service. Старые события после перезапуска не воспроизводятся.

Повторные нарушения увеличивают длительность решения в четыре раза, но не более 24 часов. Долгая спокойная работа сбрасывает эскалацию.

Для счёта уникальных пользователей хранятся хеши, а не реальные имена. Пароли, токены, cookies, тела запросов и query-параметры в решения не записываются.

Статусы и счётчики

Защита входа и SSH

  • Состояние: доступен ли локальный management bridge и отвечает ли SG InfoSec.
  • Активных блокировок: решения, срок которых ещё не истёк и которые не были отозваны.
  • Allowlist: число действующих исключений.
  • Последняя синхронизация: время последнего успешного чтения данных панелью, а не время последней атаки.

Web Shield

  • Проверено запросов: запросы, прошедшие через guard текущего процесса панели.
  • Заблокировано: сумма WAF-блокировок и ограничений частоты.
  • Новых событий: записи журнала, ещё не отмеченные как просмотренные.
  • Репутационных сетей: действующие CIDR-записи локального файла репутации.

Ручная блокировка

  1. Введите один IPv4- или IPv6-адрес. CIDR в этом поле не принимается.
  2. Выберите область: вход в панель, API панели или SSH.
  3. Задайте срок от 1 до 168 часов.
  4. Укажите понятную причину длиной от 3 до 240 символов.
  5. Нажмите «Заблокировать» и убедитесь, что решение появилось в активном списке.

Область определяет действие: ssh применяется через nftables на TCP/22, а admin-login и admin-api проверяются middleware панели.

Не блокируйте собственный адрес без резервного доступа Перед экспериментом добавьте доверенный адрес администратора в allowlist или убедитесь, что у вас есть консольный доступ к серверу.

Для снятия решения найдите его в таблице «Блокировки» и нажмите «Разблокировать». Операция фиксируется в аудите.

Allowlist

Allowlist запрещает автоматическое создание решения для указанного IP или CIDR. Используйте его только для действительно доверенных административных сетей.

  • IP или CIDR: например 198.51.100.24 или 198.51.100.0/24.
  • Область: одна конкретная область либо все области.
  • Описание: кто владеет сетью и зачем сделано исключение.
  • До даты: необязательный срок. Временные исключения безопаснее бессрочных.
Не добавляйте широкие публичные сети Запись 0.0.0.0/0, ::/0 или большая сеть провайдера фактически отключит соответствующую защиту.

Веб-защита

Режимы работы

РежимПоведениеКогда применять
БлокироватьЗаписывает событие и отклоняет подтверждённый вредоносный или слишком частый запрос.Обычная постоянная работа.
Только наблюдатьОценивает и журналирует запросы, но не блокирует их.Первичная настройка и проверка порогов.
ВыключитьНе выполняет WAF-оценку и rate limit.Краткая диагностика только при подтверждённой проблеме.

Что проверяется

  • опасные методы TRACE, TRACK и CONNECT;
  • сканирование .env, .git, WordPress, phpMyAdmin, Actuator, CGI и PHPUnit;
  • path traversal и его распространённые URL-кодированные варианты;
  • высокоуверенные признаки SQL injection, XSS и command injection;
  • превышение разрешённого размера тела запроса;
  • частота запросов к входу и API.

Параметры

  • Тело запроса: максимальное число байт, которое разрешено и инспектируется.
  • Входов в минуту: лимит запросов к маршрутам входа для одного IP.
  • API-запросов в минуту: лимит защищённых API-запросов для одного IP.
  • Порог блокировки: итоговый риск 1–100, после которого режим «Блокировать» отклоняет запрос.
  • Порог уведомления: минимальный риск события для отправки webhook.

После изменения параметров нажмите «Сохранить политику». Новые значения применяются процессом панели без ручного редактирования файлов.

Репутация IP

Локальная репутация — это JSON со списком IP-сетей и оценкой риска. При совпадении используется наиболее специфичная CIDR-запись.

{
  "entries": [
    {
      "cidr": "203.0.113.0/24",
      "score": 90,
      "country": "ZZ",
      "asn": 64500,
      "tags": ["scanner", "hosting"],
      "expires_at": "2026-12-31T23:59:59Z"
    }
  ]
}
  • cidr — обязательная IPv4- или IPv6-сеть;
  • score — обязательное число 1–100;
  • country — необязательный двухбуквенный код;
  • asn — необязательный номер автономной системы;
  • tags — до 16 коротких тегов;
  • expires_at — необязательная дата UTC; просроченные записи игнорируются.

Загрузка полностью заменяет текущий список после проверки JSON. Максимальный размер — 2 МБ, максимальное число записей — 20 000.

Уведомления

Webhook необязателен. Допускается только адрес с https://. Событие отправляется асинхронно, когда его риск не ниже настроенного порога уведомления.

В webhook передаются безопасные поля события: время, IP, действие, риск, идентификаторы правил, область и нормализованная репутация. Пароли, токены, cookies, тела и полные запросы не отправляются.

Одинаковые срабатывания одного IP подавляются в течение короткого окна, чтобы атака не создала поток одинаковых уведомлений.

Webhook не является гарантированной доставкой Основное доказательство события — локальный журнал панели и решения SG InfoSec. Ошибка внешнего получателя не должна останавливать панель.

История решений и аудит

  • Активные решения: что блокируется сейчас, область, причина и срок.
  • Последние решения: активные, истёкшие и отозванные записи.
  • Аудит: создание и отзыв решений, изменения allowlist и другие административные операции.
  • Последние срабатывания: WAF, rate limit и репутационные совпадения. «Просмотрено» меняет только отметку, а не удаляет событие.

История полезна для ответа на четыре вопроса: кто обращался, какая область была атакована, какое правило сработало и что система сделала.

Резервное копирование и откат

Обновление SG-Gateway создаёт Safety Backup до замены приложения. Отдельный этап интеграции сохраняет systemd-unit панели, source-конфигурацию bridge, unit bridge и tmpfiles-контракт. При ошибке этапа эти файлы возвращаются автоматически.

Установщик SG InfoSec сохраняет существующие конфигурацию и SQLite-состояние при повторном запуске. Обычное удаление бинарников также может сохранить данные; purge предназначен для явного удаления состояния.

Перед ручными изменениями

  1. Сохраните резервную копию SG-Gateway через Maintenance.
  2. Не редактируйте SQLite SG InfoSec вручную.
  3. Не создавайте собственные объекты внутри таблицы inet sg_infosec.
  4. Запишите текущие значения режима, порогов, allowlist и репутации.

Диагностика

Быстрая проверка

sudo sg-infosecctl health
sudo sg-infosecctl status
sudo sg-infosecctl decisions list
sudo sg-infosecctl allowlist list
sudo sg-infosecctl nft status
sudo sg-infosecctl nft list

Службы и журналы

sudo systemctl status \
  sg-infosec-enforcer.service \
  sg-infosec.service \
  sg-infosec-management-bridge.service \
  sg-gateway.service

sudo journalctl \
  -u sg-infosec-enforcer.service \
  -u sg-infosec.service \
  -u sg-infosec-management-bridge.service \
  -u sg-gateway.service \
  --since '-15 minutes' --no-pager

Типичные состояния

  • «Недоступен» в карточке: проверьте core service, management bridge и сокеты в /run/sg-infosec.
  • SSH-решение есть, но nftables пуст: проверьте enforcer и выполните sudo sg-infosecctl nft reconcile.
  • Панель работает, но настройки не сохраняются: проверьте bridge, права на /var/lib/sg-gateway/infosec и журнал панели.
  • Ложное WAF-срабатывание: временно включите «Только наблюдать», найдите правило в событиях и скорректируйте пороги. Не отключайте всю систему без необходимости.

Ограничения

  • Это не антивирус, не сетевой IDS/IPS и не анализатор всего VPN-трафика.
  • Веб-фильтр — компактный набор правил для SG-Gateway, а не полный OWASP Core Rule Set.
  • Репутация локальная: система сама не загружает глобальные списки и не обменивается ими с другими серверами.
  • GeoIP и ASN учитываются только тогда, когда администратор передал их в локальном файле репутации.
  • Webhook зависит от внешнего получателя и сети.
  • При недоступности SG InfoSec интеграция панели работает по модели fail-open: административная панель не должна стать недоступной только из-за сбоя защитного демона.
  • Повреждение или неизвестные объекты внутри принадлежащей SG InfoSec таблицы nftables приводят к отказу от опасной перезаписи, а не к удалению чужих правил.
Практический режим Для постоянной работы используйте режим «Блокировать», разумные лимиты, узкий allowlist и резервный консольный доступ. После крупных изменений сначала просмотрите события в режиме наблюдения.
