# SG InfoSec: полное руководство

SG InfoSec — локальная система защиты SG-Gateway, административного API и SSH. Она состоит из отдельного движка принятия решений, минимального root-enforcer для nftables, интеграции с SG-Gateway, Web Shield, локальной репутации IP и журнала событий.

Система не имеет публичного API, не анализирует VPN-трафик клиентов и не должна изменять AWG, подписки или VPN-порты 585–587.

## Что защищает система

SG InfoSec закрывает четыре группы рисков.

1. **SSH.** Быстрый и медленный brute force, перебор имён пользователей и связанные атаки на несколько сервисов.
2. **Вход в SG-Gateway.** Повторные ошибки пароля и решения области `admin-login`.
3. **API панели.** Ошибки авторизации, чрезмерная частота запросов и решения области `admin-api`.
4. **HTTP-атаки.** Высокоуверенные признаки SQL injection, XSS, path traversal, command injection, опасные HTTP-методы и известные пути сканеров.

Архитектура разделена по привилегиям:

- `sg-infosecd` работает без root, читает журналы, хранит SQLite, применяет политики и обслуживает Unix control/event API;
- `sg-infosec-enforcerd` работает с минимальной root-привилегией и управляет только таблицей `inet sg_infosec`;
- `sg-infosec-management-bridge` даёт панели строго ограниченные операции чтения и управления через Unix-сокет;
- SG-Gateway применяет решения входа/API и Web Shield до выполнения защищённого обработчика.

## Быстрый старт после установки

После установки проверьте службы:

```bash
sudo systemctl status \
  sg-infosec-enforcer.service \
  sg-infosec.service \
  sg-infosec-management-bridge.service \
  sg-gateway.service
```

Проверьте локальные API и nftables:

```bash
sudo sg-infosecctl health
sudo sg-infosecctl status
sudo sg-infosecctl nft status
sudo sg-infosecctl nft list
```

Откройте в панели:

```text
Security → SG InfoSec
```

Нормальное исходное состояние:

- статус `Работает`;
- активных блокировок `0`;
- management bridge активен;
- Web Shield находится в режиме `Блокировать` или в выбранном администратором режиме;
- таблица nftables готова, но может не содержать адресов до первого SSH-решения.

Не создавайте серию неправильных входов со своего единственного административного IP без allowlist или консольного доступа.

## Автоматическая защита SSH

SG InfoSec читает только новые записи:

- `ssh.service`;
- `sshd.service`;
- `nginx.service`;
- `sg-gateway.service`.

Старые журналы после перезапуска не воспроизводятся.

Пороговые сценарии по умолчанию:

| Сценарий | Порог | Результат |
|---|---:|---|
| Быстрый SSH brute force | 5 ошибок за 10 минут | SSH-решение |
| Медленный SSH brute force | 12 ошибок за 60 минут | SSH-решение |
| Перебор пользователей | 6 разных имён за 15 минут | SSH-решение |
| Сканирование административных путей | 6 запросов за 5 минут | API-решение |
| Ошибки входа в панель | 5 ошибок за 10 минут | Login-решение |
| Ошибки авторизации API | 10 ошибок за 10 минут | API-решение |
| Связанная атака | риск от двух и более сервисов | решения только представленных областей |

SSH-решение применяется через nftables только к TCP/22. Оно не создаёт all-port ban.

Повторные нарушения увеличивают срок решения в четыре раза, но не более 24 часов. После длительного спокойного периода эскалация сбрасывается.

В памяти хранится ограниченное число IP-состояний. Имена пользователей используются только в виде хешей. Пароли, cookies, токены, query string и тела запросов в решение не записываются.

## Защита панели и API

Перед обработкой защищённого запроса SG-Gateway проверяет решение по трём параметрам:

- источник решения;
- область (`admin-login` или `admin-api`);
- канонический IPv4/IPv6 адрес.

Активное решение приводит к временному отказу запроса. Ошибки авторизации отправляются в SG InfoSec как события и участвуют в корреляции.

Области не взаимозаменяемы:

- `admin-login` ограничивает вход в панель;
- `admin-api` ограничивает защищённый API;
- `ssh` ограничивает TCP/22 через nftables.

Это позволяет заблокировать конкретный административный канал, не отключая VPN и другие сервисы.

## Веб-защита

Web Shield работает в одном из трёх режимов.

### Блокировать

Запрос оценивается, событие записывается, а подтверждённая атака или превышение лимита отклоняется.

Это стандартный режим постоянной работы.

### Только наблюдать

Запрос оценивается и записывается, но не блокируется.

Используйте режим:

- после первого включения на нестандартной установке;
- при проверке ложного срабатывания;
- перед существенным изменением порогов.

### Выключить

WAF и rate limit не применяются.

Используйте только кратковременно для подтверждённой диагностики. Автоматическая защита SSH отдельного SG InfoSec при этом не отключается.

### Проверки Web Shield

Web Shield проверяет:

- методы `TRACE`, `TRACK`, `CONNECT`;
- пути `.env`, `.git`, `wp-admin`, `wp-login.php`, `phpmyadmin`, `server-status`, `actuator`, `cgi-bin`, `vendor/phpunit`;
- path traversal и распространённые URL-кодированные варианты;
- SQL injection высокого уровня уверенности;
- XSS высокого уровня уверенности;
- command injection;
- превышение допустимого размера тела;
- частоту запросов к входу и API;
- локальную репутацию IP.

Это компактный фильтр, ориентированный на SG-Gateway. Он не является полным OWASP Core Rule Set.

### Настройки

| Параметр | Назначение |
|---|---|
| `Тело запроса, байт` | Максимально разрешённое и инспектируемое тело |
| `Входов в минуту` | Лимит запросов входа с одного IP |
| `API-запросов в минуту` | Лимит защищённых API-запросов с одного IP |
| `Порог блокировки` | Итоговый риск 1–100 для блокировки |
| `Порог уведомления` | Минимальный риск для webhook |
| `HTTPS webhook` | Необязательный адрес получателя событий |

Допустимые пределы проверяются сервером. Настройки записываются атомарно и применяются работающим движком.

## Репутация IP и сетей

Локальная репутация загружается JSON-объектом:

```json
{
  "entries": [
    {
      "cidr": "203.0.113.0/24",
      "score": 90,
      "country": "ZZ",
      "asn": 64500,
      "tags": ["scanner", "hosting"],
      "expires_at": "2026-12-31T23:59:59Z"
    }
  ]
}
```

Поля:

- `cidr` — обязательный IPv4/IPv6 адрес или сеть;
- `score` — обязательное число от 1 до 100;
- `country` — необязательный двухбуквенный код;
- `asn` — необязательный номер автономной системы;
- `tags` — до 16 коротких тегов;
- `expires_at` — необязательная дата UTC.

При совпадении нескольких сетей используется наиболее специфичная CIDR-запись.

Ограничения:

- не более 20 000 записей;
- файл не более 2 МБ;
- просроченные записи игнорируются;
- загрузка после проверки полностью заменяет текущий список.

SG InfoSec не загружает внешнюю репутацию автоматически. Страна и ASN учитываются только тогда, когда они присутствуют в локальном файле.

## Уведомления

Webhook должен использовать `https://`.

Событие отправляется асинхронно, когда его риск достигает настроенного порога. Передаются только безопасные поля:

- время;
- IP;
- действие;
- риск;
- идентификаторы правил;
- область;
- нормализованная репутация.

Не передаются:

- пароль;
- токен;
- cookie;
- тело запроса;
- полный URL с query string;
- имя пользователя в открытом виде.

Идентичные события одного источника подавляются в коротком окне, чтобы атака не создавала поток одинаковых webhook-запросов.

Webhook — дополнительный канал. Локальный журнал и SQLite остаются источником истины. Недоступность внешнего получателя не должна останавливать SG-Gateway.

## Ручные блокировки

В панели заполните:

1. IP-адрес;
2. область;
3. срок от 1 до 168 часов;
4. причину от 3 до 240 символов.

Для ручной блокировки принимается один IPv4/IPv6 адрес, не CIDR.

Области:

- `Вход в панель` → `admin-login`;
- `API панели` → `admin-api`;
- `SSH` → `ssh`.

После создания решение должно появиться в активном списке.

Снять решение можно кнопкой `Разблокировать`. Отзыв фиксируется в аудите и для nftables-решения приводит к повторной синхронизации kernel state.

CLI-пример ручной SSH-блокировки:

```bash
sudo sg-infosecctl decisions add \
  --source local-admin \
  --scope ssh \
  --backend nftables \
  --ip 203.0.113.10 \
  --duration 30m \
  --reason "incident response"
```

Перед блокировкой собственного адреса обеспечьте альтернативный доступ к серверу.

## Allowlist

Allowlist предотвращает автоматическое создание решения для доверенного адреса или сети.

Поля панели:

- `IP или CIDR`;
- область или все области;
- описание;
- необязательный срок.

Рекомендуется:

- добавлять только административные адреса;
- указывать владельца и причину;
- использовать срок для временного доступа;
- регулярно удалять устаревшие записи.

Не добавляйте:

- `0.0.0.0/0`;
- `::/0`;
- широкую сеть публичного провайдера;
- адрес неизвестного VPN или proxy.

Слишком широкий allowlist фактически отключает защиту соответствующей области.

## История и аудит

Панель показывает четыре независимых вида данных.

### Активные решения

Действующие блокировки, область, причина и срок окончания.

### Последние решения

Активные, истёкшие и отозванные решения.

### Аудит

Административные операции: создание/отзыв решений, изменения allowlist и результат операции.

### События Web Shield

Время, IP, риск, реакция, правила и репутация.

Кнопка `Просмотрено` меняет только отметку события. Она не удаляет запись и не снимает блокировку.

## Резервное копирование и откат

Обновление SG-Gateway создаёт Safety Backup до замены приложения.

Этап SG InfoSec интеграции отдельно сохраняет:

- `/etc/systemd/system/sg-gateway.service`;
- `/etc/sg-infosec/sources.d/sg-gateway-management.yaml`;
- `/etc/systemd/system/sg-infosec-management-bridge.service`;
- `/usr/lib/tmpfiles.d/sg-infosec-management-bridge.conf`.

При ошибке интеграции эти файлы возвращаются, systemd перечитывает unit-файлы, SG InfoSec перезапускается при необходимости, а панель запускается в прежнем состоянии.

Повторный запуск установщика SG InfoSec сохраняет:

- `/etc/sg-infosec`;
- `/var/lib/sg-infosec/sg-infosec.db`;
- существующие policy/source файлы;
- действующие решения и аудит.

Основные пути SG InfoSec:

```text
/etc/sg-infosec/sg-infosec.yaml
/etc/sg-infosec/detection-rules.json
/etc/sg-infosec/sources.d/
/etc/sg-infosec/policies.d/
/var/lib/sg-infosec/sg-infosec.db
/run/sg-infosec/events.sock
/run/sg-infosec/control.sock
/run/sg-infosec/enforcer.sock
```

Основные пути интеграции SG-Gateway:

```text
/var/lib/sg-gateway/infosec/guard.json
/var/lib/sg-gateway/infosec/reputation.json
/var/lib/sg-gateway/infosec/alerts.jsonl
/run/sg-infosec-bridge/management.sock
```

Перед ручными изменениями:

1. создайте backup через Maintenance;
2. сохраните текущую конфигурацию;
3. не редактируйте SQLite вручную;
4. не добавляйте собственные правила внутрь `inet sg_infosec`;
5. не удаляйте Unix-сокеты работающих служб вручную.

## Диагностика

### Состояние SG InfoSec

```bash
sudo sg-infosecctl health
sudo sg-infosecctl status
sudo sg-infosecctl decisions list
sudo sg-infosecctl allowlist list
sudo sg-infosecctl audit list
sudo sg-infosecctl nft status
sudo sg-infosecctl nft list
```

### Синхронизация nftables

```bash
sudo sg-infosecctl nft reconcile
```

Используйте, если активное SSH-решение присутствует в SQLite, но не отражено в kernel set.

### Службы

```bash
sudo systemctl is-active sg-infosec-enforcer.service
sudo systemctl is-active sg-infosec.service
sudo systemctl is-active sg-infosec-management-bridge.service
sudo systemctl is-active sg-gateway.service
```

### Журналы

```bash
sudo journalctl \
  -u sg-infosec-enforcer.service \
  -u sg-infosec.service \
  -u sg-infosec-management-bridge.service \
  -u sg-gateway.service \
  --since '-15 minutes' \
  --no-pager
```

### Проверка конфигурации

```bash
sudo sg-infosecctl config validate
```

### Типичные проблемы

#### Панель показывает «Недоступен»

Проверьте:

1. `sg-infosec.service`;
2. `sg-infosec-management-bridge.service`;
3. наличие `/run/sg-infosec/control.sock`;
4. наличие `/run/sg-infosec-bridge/management.sock`;
5. журнал обеих служб.

#### SSH-решение не попало в nftables

Проверьте enforcer и выполните reconcile. Если таблица была изменена неизвестными правилами, enforcer может отказаться от опасной перезаписи.

#### Настройки Web Shield не сохраняются

Проверьте:

- права на `/var/lib/sg-gateway/infosec`;
- журнал `sg-gateway.service`;
- валидность числовых диапазонов;
- `https://` у webhook;
- JSON репутации и его размер.

#### Подозрение на ложное WAF-срабатывание

1. включите `Только наблюдать`;
2. повторите безопасный запрос;
3. найдите rule ID и risk score в событиях;
4. скорректируйте порог или запрос;
5. верните режим `Блокировать`.

Не отключайте SG InfoSec целиком для диагностики одного HTTP-правила.

## Ограничения и модель отказа

SG InfoSec не является:

- антивирусом;
- Suricata-подобным IDS/IPS;
- полным Wazuh;
- анализатором VPN-трафика;
- полным OWASP CRS;
- глобальной сетью репутации.

Web Shield видит только запрос, который дошёл до SG-Gateway. Он не анализирует произвольные сетевые пакеты.

SG-Gateway использует модель `fail-open` для application-решений: сбой SG InfoSec сам по себе не должен закрыть владельцу доступ к панели. Ошибка защитного модуля журналируется, но панель продолжает работать.

SSH-enforcement отделён от панели. Root-enforcer имеет право только на собственную таблицу nftables и фиксированные типы решений. Неизвестная схема внутри owned table приводит к отказу операции, а не к удалению чужих объектов.

SQLite является источником истины, nftables timeout sets — enforcement-кэшем.

## Рекомендуемая постоянная конфигурация

- Web Shield: `Блокировать`;
- лимит входа: оставить умеренным, не снижать без анализа журналов;
- API limit: учитывать автоматические панели и интеграции;
- allowlist: только узкие доверенные адреса;
- webhook: HTTPS-получатель без секретов в URL;
- резервный доступ: консоль или отдельный доверенный IP;
- регулярный просмотр: активные решения, непросмотренные события и аудит.

После изменения порогов или загрузки большой репутации используйте режим наблюдения, проверьте реальные события и только затем включайте блокировку.
